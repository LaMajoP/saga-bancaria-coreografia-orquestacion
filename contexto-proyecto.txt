======================================================================
DISTRIBUCIÓN DE TRABAJO
TALLER PRÁCTICO AVANZADO — PATRÓN SAGA BANCARIO
===============================================

PROYECTO:
NovaBank International — Transacciones Distribuidas con Saga

OBJETIVO:
Implementar un sistema bancario distribuido capaz de ejecutar
transferencias interbancarias utilizando el Patrón Saga, demostrando
tanto Orquestación como Coreografía, manejo de fallos, compensaciones,
consistencia eventual, idempotencia y observabilidad.

======================================================================

1. CONTEXTO DEL TALLER
   ======================================================================

El equipo representa al área de arquitectura e ingeniería del banco
privado "NovaBank International".

El banco procesa transferencias interbancarias de alto valor y necesita
abandonar mecanismos tradicionales basados en bloqueos globales de
bases de datos, como Two-Phase Commit (2PC).

La solución debe utilizar el Patrón Saga bajo el modelo BASE:

```
Basically Available
Soft state
Eventual consistency
```

El objetivo principal del taller es demostrar correctamente:

```
- Transacciones distribuidas.
- Manejo de fallos.
- Consistencia eventual.
- Transacciones locales.
- Compensaciones.
- Compensaciones ejecutadas en orden inverso.
- Idempotencia.
- Diferencia entre Orquestación y Coreografía.
- Observabilidad del flujo.
```

======================================================================
2. REQUISITOS OBLIGATORIOS DEL TALLER
=====================================

El sistema debe contar con las siguientes capas.

---

## 2.1 FRONTEND + SIMULADOR DE CAOS

Debe permitir:

```
- Ingresar cuenta origen.
- Ingresar cuenta destino.
- Ingresar importe.
- Ejecutar una transferencia.
- Activar errores intencionalmente.
- Visualizar el avance de cada paso.
- Visualizar las compensaciones.
- Mostrar los estados de la Saga en tiempo real.
```

El frontend debe permitir demostrar fácilmente los casos de prueba
solicitados por el taller.

---

## 2.2 BACKEND / API GATEWAY

Debe funcionar como punto de entrada central.

Responsabilidades principales:

```
- Recibir solicitudes del frontend.
- Generar/utilizar identificadores de idempotencia UUID.
- Registrar la transferencia.
- Despachar las operaciones hacia los servicios bancarios.
- Devolver el estado de la operación.
```

---

## 2.3 MICROSERVICIOS DE DOMINIO BANCARIO

Se requieren como mínimo tres microservicios independientes.

MICROSERVICIO 1:
Account & Ledger

Responsabilidades:

```
- Débitos.
- Créditos.
- Reversas de balance.
- Registro de movimientos.
```

MICROSERVICIO 2:
Risk / Fraud

Responsabilidades:

```
- Reglas de validación.
- Prevención de fraude.
- Límites diarios.
- Aprobación/rechazo de operaciones.
```

MICROSERVICIO 3:
Interbank Clearing Gateway

Responsabilidades:

```
- Simular la liquidación externa.
- Simular fallos de red.
- Simular timeouts.
- Confirmar o rechazar operaciones.
```

Cada servicio debe tener almacenamiento propio y desacoplado,
utilizando Database-per-Service o esquemas lógicamente aislados.

---

## 2.4 PATRÓN SAGA

Esta es la parte de mayor peso en la evaluación.

El sistema debe:

```
- Coordinar transacciones locales.
- Detectar fallos.
- Ejecutar compensaciones.
- Ejecutar las compensaciones en orden inverso.
- Evitar estados inconsistentes.
- Demostrar tanto Orquestación como Coreografía.
```

---

## 2.5 OBSERVABILIDAD

Debe existir un mecanismo de observabilidad utilizando Prefect o
una alternativa equivalente.

Debe permitir visualizar:

```

======================================================================
3. ORQUESTACIÓN VS COREOGRAFÍA
==============================

El taller exige implementar las DOS modalidades.

---

## 3.1 SAGA ORQUESTADA

Existe un orquestador central.

El orquestador:

```
1. Ordena ejecutar una operación.
2. Espera su resultado.
3. Continúa con el siguiente servicio.
4. Detecta un fallo.
5. Identifica qué operaciones anteriores tuvieron éxito.
6. Ejecuta explícitamente las compensaciones.
```

Ejemplo:

```
Account Debit
      |
      v
Risk Check
      |
      v
Clearing
      |
      X FALLA
      |
      v
Compensate Risk
      |
      v
Compensate Debit
```

---

## 3.2 SAGA COREOGRAFIADA

No existe un coordinador central.

Los servicios se comunican mediante eventos.

Ejemplo:

```
TransferenciaSolicitada
        |
        v
SaldoDebitado
        |
        v
RiesgoAprobado
        |
        v
ClearingSolicitado
        |
        v
TransferenciaCompletada
```

Si ocurre un fallo:

```
TransferenciaFallida
```

Los servicios que corresponda reaccionan autónomamente y ejecutan
sus propias compensaciones.

4. CASOS DE PRUEBA OBLIGATORIOS
===============================

CP-01 — CAMINO FELIZ

```
Transferencia normal sin errores.
```

Debe ocurrir:

```
- Débito en cuenta origen.
- Aprobación de riesgo.
- Liquidación interbancaria.
- Crédito en cuenta destino.
```

Resultado:

```
CONFIRMADO
```

---

## CP-02 — FONDOS INSUFICIENTES

El monto de la transferencia supera el saldo disponible.

Debe ocurrir:

```
- Rechazo inmediato.
- No deben ejecutarse compensaciones.
- No deben modificarse los saldos.
```

Resultado:

```
RECHAZADO_FONDOS
```

---

## CP-03 — FALLA DE RIESGO / ANTIFRAUDE

Se activa un switch para forzar el fallo de riesgo.

Debe ocurrir:

```
1. Se realiza el débito.
2. Risk/Fraud rechaza la operación.
3. Se inicia compensación.
4. Se revierte el débito.
```

Resultado:

```
- Saldo origen completamente restaurado.
- Estado RECHAZADO_RIESGO.
```

---

## CP-04 — CAÍDA / TIMEOUT DE RED EXTERNA

Se activa un switch para provocar un timeout en Clearing.

Debe ocurrir:

```
1. Se realiza el débito.
2. Riesgo aprueba.
3. Clearing falla.
4. Se anula la aprobación de riesgo.
5. Se revierte el débito.
6. Se registra auditoría.
```

Resultado:

```
- Saldos íntegros.
- Estado RECHAZADO_RED.
- Bitácora de auditoría.
```

---

## CP-05 — IDEMPOTENCIA

Se reenvía la misma operación utilizando el mismo identificador.

Debe ocurrir:

```
- El sistema reconoce el duplicado.
- No se realiza un segundo débito.
- No se realiza un segundo cobro.
- Los reintentos no modifican los saldos.
```

Objetivo:

```
Demostrar que una transferencia no puede ejecutarse dos veces
accidentalmente debido a reintentos.
```

```
- Consultar cuenta.

- Debitar.
- Acreditar.
- Registrar movimientos.
- Revertir débitos.
- Revertir créditos.

Debe garantizar:

```

- Registrar cada movimiento.

```

## 5.3 RISK / FRAUD SERVICE

Construir el servicio de riesgo.

Debe permitir:

```
- Evaluar una transferencia.
- Aprobar una transferencia.
- Rechazar una transferencia.
- Aplicar reglas de riesgo.

- Registrar la evaluación.
- Compensar/cancelar la aprobación cuando sea necesario.
```

---

## 5.4 CLEARING GATEWAY SERVICE

Construir el servicio que simula el sistema externo de liquidación.

Debe permitir:

```
- Recibir una solicitud de clearing.
- Procesar una transferencia.
- Simular latencia.
- Simular timeout.
- Confirmar operación.
- Rechazar operación.
- Ejecutar compensación cuando corresponda.
```

---

## 5.5 BASE DE DATOS

Integrar los microservicios con la base de datos.

IMPORTANTE:

```
Cada microservicio debe mantener sus datos aislados.
```

Aunque se utilice una misma instancia PostgreSQL/Supabase, los
dominios no deben acceder directamente a las estructuras de datos
de otros servicios.

Ejemplo:

```
Account Service
    -> cuentas
    -> movimientos

Risk Service
    -> evaluaciones de riesgo
    -> reglas/resultados

Clearing Service
    -> operaciones de clearing
    -> estados de liquidación
```

---

## 5.6 IDEMPOTENCIA

Implementar el mecanismo que impide dobles cobros.

Debe utilizar:

```
UUID / Idempotency-Key
```

Ejemplo:

```
Primera solicitud:
    transfer_id = ABC

    -> ejecuta débito.

Segunda solicitud:
    transfer_id = ABC

    -> NO ejecuta otro débito.
    -> devuelve el resultado existente.
```

```

3. Cambiar estado a compensación.
4. Ejecutar compensaciones en orden inverso.
5. Registrar cada compensación.
6. Finalizar como compensado/rechazado.
```

## 5.12 COMPENSACIONES

Regla fundamental:

```

```
Debit
   |
   v
Risk
   |
   v
Clearing
   |
   X FALLA
   |
   v
Compensate Risk
   |
   v
Compensate Debit
```

Nunca debe compensarse una operación que nunca se ejecutó.

## 5.14 CONSISTENCIA EVENTUAL / BASE

- El sistema puede pasar temporalmente por estados intermedios.
- La Saga finalmente lleva el sistema a un estado consistente.
- Las compensaciones restauran el estado cuando ocurre un fallo.
```
